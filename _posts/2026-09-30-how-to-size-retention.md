관측 도구를 도입할 때 반드시 나오는 질문이 있다.

**"디스크 N 테라면 며칠 치를 보관할 수 있습니까?"**

여기에 "보통 2주쯤" 이라고 답하는 걸 자주 본다. 답하는 쪽도 근거가 없고 듣는 쪽도
확인할 방법이 없다. 그런데 이건 **추측할 필요가 없는 질문**이다. 이미 쌓아둔 데이터가
있으면 거기서 바로 나온다.

## 필요한 숫자는 하나뿐이다

```
보존 가능 일수 = 가용 디스크 ÷ 일일 적재량
일일 적재량   = 하루 이벤트 수 × 이벤트 1건당 디스크 바이트
```

하루 이벤트 수는 고객이 안다. 가용 디스크도 안다. 모르는 건 **이벤트 1건이 디스크에서
몇 바이트를 차지하는가** 하나다.

그리고 이 값은 재면 된다. 24 시간을 기다릴 필요도 없다.

## 재는 법

ClickHouse 라면 `system.parts` 가 답을 갖고 있다.

```sql
SELECT table,
       sum(rows)                              AS rows,
       formatReadableSize(sum(bytes_on_disk)) AS disk,
       round(sum(bytes_on_disk) / sum(rows), 1) AS bytes_per_row
FROM system.parts
WHERE database = 'otel' AND active
GROUP BY table
ORDER BY sum(bytes_on_disk) DESC
```

주의할 점은 `bytes_on_disk` 를 봐야 한다는 것이다. `data_uncompressed_bytes` 는 압축
전 크기라 실제 디스크 사용량과 다르다. 디스크를 얼마나 먹느냐가 질문이니 압축 후를
본다.

## 실제로 재보면 — 파생 테이블이 절반 가까이 먹는다

한 번 재봤을 때 이런 모양이 나왔다.

```
원본 스팬 테이블        8.9 억 행    55.33 GiB    66.4 B/행
트레이스 요약           8.9 억 행    24.84 GiB    30.0 B/행
로그                    7.4 억 행    22.64 GiB    32.8 B/행
트레이스 ID 인덱스      8.9 억 행    17.23 GiB    20.8 B/행
세션 요약               1.9 억 행     5.13 GiB    29.4 B/행
메트릭(sum)             2.4 억 행     1.52 GiB     6.8 B/행
그 외                                 0.47 GiB
───────────────────────────────────────────────
합계                                137.3 GB
```

여기서 놓치기 쉬운 게 보인다. **원본 스팬은 55.33 GiB 인데, 그 스팬에서 파생된
요약·인덱스·세션이 47.20 GiB 를 더 먹는다.** 원본의 0.85 배다.

용량 산정에서 원본만 세면 **절반 가까이 과소 계상한다.** 실제로 도입 검토 자료에서
"스팬 1건에 약 66 바이트" 같은 숫자를 보게 되는데, 그건 원본 테이블만 본 것이다.

## 그래서 기준을 무엇으로 잡나

파생 테이블까지 포함해 **"스팬 1건이 최종적으로 몇 바이트를 남기는가"** 로 환산하는
편이 쓰기 좋다.

```
스팬 8.95 억 건 + 그에 딸린 로그 7.42 억 건  →  137.3 GB
→ 스팬 1건당 153.5 B
```

이 값 하나면 역산이 된다. 하루 15 억 스팬이면

```
15 억 × 153.5 B ≈ 230 GB/일
```

가용 디스크가 1.5 TiB 면 **약 7 일**이다. "2주쯤" 이라고 답했으면 두 배 틀렸을 것이다.

## 합성 데이터로 재면 나쁘게 나온다

여기에 한 가지 함정이 있다. **부하 생성기로 만든 데이터는 압축이 잘 안 된다.**

컬럼 지향 저장은 비슷한 값이 붙어 있을수록 잘 눌린다. 그런데 합성 데이터는 속성값을
난수로 만드는 경우가 많아서 압축률이 최악에 가깝다. 실제 트래픽은 같은 URL, 같은
사용자 에이전트, 같은 오류 메시지가 반복되므로 훨씬 잘 눌린다.

한 환경에서 압축비를 비교해보니 이렇게 갈렸다.

```
합성 트래픽      7.6 배
실제 트래픽     14.7 배
                 ─────
차이             1.9 배
```

즉 합성으로 잰 값을 그대로 쓰면 **실제보다 보수적인 숫자**가 나온다. 나쁜 방향의
오차는 아니지만, 고객에게 안내할 때는 이 폭을 같이 말하는 편이 낫다.

```
합성 실측 그대로   230 GB/일  →   7 일
실측 압축비 적용   119 GB/일  →  14 일
```

**7~14 일** 이라고 답하고, 현장 데이터로 2 주쯤 재본 뒤 확정하는 것이 정직하다.

## 왜 24 시간 시험을 안 해도 되나

"하루 돌려보고 재자" 는 자연스러운 발상이지만, 보존 기간 질문에는 필요가 없다.
필요한 건 **행당 바이트** 하나이고 그건 이미 쌓인 데이터에서 나온다.

24 시간 시험이 필요한 경우는 따로 있다. **시간대별 부하 편차**를 보고 싶을 때다.
피크가 평균의 몇 배인지는 하루를 봐야 안다. 하지만 그건 용량 산정이 아니라 성능
설계 질문이다. 두 질문을 섞지 않는 편이 좋다.

## 보존 기간을 늘려야 한다면

디스크를 늘리는 것 말고 방법이 하나 더 있다. **계층 보존**이다.

원본은 짧게 두고, 롤업(1 분 단위 집계)은 길게 둔다. 롤업은 원본의 수천 분의 일
크기라 90 일을 둬도 부담이 없다.

```
원본 스팬    30 일   →  개별 트레이스를 파고들 수 있는 기간
1분 롤업     90 일   →  추이·비교를 볼 수 있는 기간
```

"지난 분기 대비" 같은 질문은 롤업으로 답할 수 있고, "그때 그 요청이 왜 느렸나" 는
원본이 있어야 답한다. **필요한 기간이 서로 다르다는 점**을 이용하는 것이다.

다만 이렇게 하면 차트에는 보이는데 눌러도 원본이 없는 구간이 생긴다. 도입할 때
설명하고 넘어가야 나중에 버그로 오해받지 않는다.

## 정리

```
1. bytes_on_disk 를 행 수로 나눈다        ← 압축 후 값을 봐야 한다
2. 파생 테이블을 전부 더한다               ← 빼먹으면 절반 가까이 과소 계상
3. 이벤트 1건당 바이트로 환산한다
4. 하루 이벤트 수를 곱한다
5. 가용 디스크를 나눈다
```

다섯 줄이면 끝나는 계산이다. "보통 며칠" 이라고 답하는 대신 이 다섯 줄을 보여주면
고객도 자기 환경에서 다시 계산해볼 수 있다.
