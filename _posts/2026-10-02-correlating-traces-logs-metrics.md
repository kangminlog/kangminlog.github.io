관측 도구 소개에는 늘 "세 가지 신호를 통합합니다" 가 나온다. 그런데 **무엇으로**
묶는지는 잘 설명하지 않는다. 한 화면에 나란히 놓는 것과 실제로 연결되는 것은 다르다.

묶는 열쇠는 결국 두 개다. **식별자**와 **리소스 속성**이다.

## 트레이스 하나가 무엇인지부터

요청 하나가 서비스 여러 개를 거친다고 하자.

```
사용자 → 주문 API → 재고 서비스 → DB
```

각 구간의 작업을 스팬(span)이라 부르고, 이 요청 전체를 트레이스(trace)라 부른다.
스팬마다 두 개의 식별자가 붙는다.

```
trace_id   32 자리 16진수   요청 전체에 하나
span_id    16 자리 16진수   구간마다 하나
parent_span_id              나를 부른 구간
```

`trace_id` 가 같은 스팬을 모으면 요청 하나가 복원되고, `parent_span_id` 를 따라가면
호출 관계가 나온다. 트리를 만드는 데 필요한 정보가 이게 전부다.

## 프로세스를 넘어갈 때

문제는 주문 API 와 재고 서비스가 **다른 프로세스**라는 점이다. 메모리를 공유하지 않는다.
그래서 식별자를 요청에 실어 보낸다. W3C 가 정한 표준 헤더가 있다.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^------------ trace_id -------^ ^--- span_id ---^ ^^
             버전                                                 플래그
```

주문 API 는 자기 `span_id` 를 이 헤더에 담아 재고 서비스를 부른다. 재고 서비스의
에이전트는 헤더를 읽어 **같은 `trace_id` 를 쓰고, 받은 `span_id` 를 자기 부모로 삼는다.**

이게 전부다. 마법은 없고, 헤더 하나를 이어 붙이는 규약이 있을 뿐이다. 그리고 이 규약이
W3C 표준이라 **다른 언어, 다른 회사 제품끼리도 이어진다.**

에이전트가 하는 일의 절반이 이 헤더를 자동으로 넣고 읽는 것이다. 직접 계측하면
HTTP 클라이언트마다 손으로 넣어야 한다.

## 로그를 어떻게 붙이나

로그 레코드에도 `trace_id` 와 `span_id` 필드가 있다. 자바 에이전트를 쓰면 로그 출력
시점의 컨텍스트에서 자동으로 채워진다.

그래서 이런 일이 가능해진다. **느린 요청 하나를 화면에서 열면, 그 요청이 남긴 로그만
골라서 보여준다.** 시간으로 어림잡아 찾는 게 아니라 식별자로 정확히 고른다.

실무에서 효과가 가장 큰 것이 이 연결이라고 생각한다. 장애 조사에서 제일 오래 걸리는
일이 "그 요청이 남긴 로그 찾기" 인데, 그게 클릭 한 번이 된다.

반대 방향도 된다. 에러 로그 한 줄에서 **그 요청이 어디를 거쳤는지**로 건너뛰는 것이다.
로그만 보면 어느 서비스가 원인인지 알 수 없는 경우가 많은데, 트레이스로 넘어가면
바로 보인다.

## 메트릭은 사정이 다르다

메트릭은 이미 집계된 값이다. "지난 1분 평균 응답시간 240 ms" 에는 개별 요청이 남아
있지 않다. 평균을 낸 순간 원본이 사라지기 때문에 `trace_id` 를 붙일 데가 없다.

그래서 **exemplar** 라는 장치가 있다. 집계값 옆에 그 구간을 대표하는 샘플 몇 개의
`trace_id` 를 같이 남긴다.

```
p99 = 4.2s   ← exemplar: trace_id=4bf92f35...
```

"p99 가 튀었다" 를 보고 **실제로 4.2 초 걸린 요청 하나로 바로 넘어갈 수 있다.**
그래프에서 트레이스로 가는 다리다.

다만 exemplar 는 지원 여부가 제품·언어마다 갈린다. 되는지 확인하고 기대하는 편이 좋다.

## 또 하나의 축 — 리소스 속성

식별자가 "같은 요청" 을 묶는다면, 리소스 속성은 **"같은 대상"** 을 묶는다.

```
service.name        order-api
service.instance.id order-api-7d9f
host.name           was-01
deployment.environment production
```

세 신호 모두 이 속성들을 달고 다닌다. 그래서 트레이스·로그·메트릭이 없어도
"`was-01` 에서 나온 것 전부" 같은 조회가 성립한다.

여기서 실무 조언이 하나 있다. **`service.name` 을 처음에 대충 정하면 나중에 고생한다.**
인스턴스마다 다르게 줄지, 클러스터 전체를 하나로 볼지에 따라 화면이 완전히 달라진다.
바꾸면 과거 데이터와 이름이 안 맞아 끊긴다. 붙이기 전에 규칙을 정해두는 게 좋다.

## 정리하면

```
같은 요청   →  trace_id · span_id      (W3C traceparent 로 프로세스 경계를 넘는다)
같은 대상   →  service.name 등 리소스 속성
집계 → 개별 →  exemplar
```

"통합" 이라는 말이 실제로 가리키는 건 이 세 줄이다. 도구를 볼 때는 화면이 예쁜지보다
**이 연결이 실제로 걸려 있는지**를 확인하는 편이 낫다. 트레이스에서 로그로 한 번
눌러보면 바로 안다.
