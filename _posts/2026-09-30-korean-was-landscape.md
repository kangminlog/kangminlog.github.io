자바 웹 애플리케이션을 올려 돌려주는 프로그램을 WAS 라고 부른다. Tomcat 이 가장 유명하고,
요즘 새로 만드는 것은 대개 Tomcat 이 애플리케이션 안에 들어간 형태(`java -jar`)로 돈다.

그런데 공공·금융·의료 현장에 들어가 보면 **JEUS · WebLogic · WebSphere** 같은 이름을
계속 만난다. 성능이 더 좋아서가 아니다. 관측 도구를 붙이는 입장에서는 이 차이가
실무에 직접 영향을 주므로, 왜 그런지와 무엇이 달라지는지를 정리한다.

## 왜 상용 WAS 를 쓰나

**첫째, 기술지원 계약.** 새벽 3시에 장애가 나면 전화를 걸 상대가 계약서에 적혀 있어야 한다.
커뮤니티 제품은 "누가 책임지나" 에 답할 주체가 없고, 제안서 심사에서 이게 그대로 감점이 된다.
기술적 판단이 아니라 조달 요건이다.

**둘째, 조달 구조.** 공공 정보화 사업은 제품 인증과 국산 소프트웨어 가산점을 요구하는
경우가 많다. 등록된 제품이냐가 실무적으로 중요하다.

**셋째, 기능 범위.** Tomcat 은 엄밀히 말하면 WAS 의 일부만 구현한다 — 웹 요청을 받아
자바 코드에 넘기는 부분(서블릿 컨테이너)까지다. 여러 데이터베이스에 걸친 트랜잭션을 한
묶음으로 처리하거나, 기업용 컴포넌트 규격(EJB)·메시징 규격(JMS)이 필요하면 Tomcat 만으로는
안 된다. 오래된 기간계 시스템이 이런 규격 위에 지어진 경우가 많다.

**넷째, 세트로 들어간다.** 국내 상용 벤더는 WAS·미들웨어·데이터베이스를 묶어 판다.
셋을 같이 도입한 곳은 WAS 만 따로 바꾸기 어려워진다.

**Tomcat 이 나빠서 안 쓰는 게 아니다.** 신규 개발에서는 Tomcat 이 압도적으로 많다.
다만 그 신규 시스템 옆에 10년 된 상용 WAS 가 같이 돌고 있는 것이 현장의 모습이다.

## 지형

```
국산 상용     JEUS                      공공·금융 레퍼런스가 두껍다
외산 상용     WebLogic · WebSphere      2000년대 대형 시스템에 많이 들어갔다
오픈소스      Tomcat · JBoss/WildFly    신규 구축의 다수
지원 붙은 OSS JBoss EAP                 "책임 문제" 를 푸는 절충안
내장형        스프링부트 내장 Tomcat     WAS 를 따로 설치하지 않는다
```

## 관측 도구 입장에서 무엇이 달라지나

에이전트에 어떤 WAS 의 전용 계측 모듈이 들어 있는지는 직접 세어볼 수 있다.

```
$ unzip -l opentelemetry-javaagent.jar \
  | grep -oE "instrumentation/[a-z0-9_-]+/" | sort -u
```

WAS 계열만 추리면 이렇게 갈린다.

```
전용 모듈 있음   tomcat  jetty  undertow  payara  liberty  grizzly
                quarkus  helidon  netty  vertx  ratpack
전용 모듈 없음   JEUS  WebLogic  WebSphere  JBoss/WildFly
```

**국내 현장에서 많이 만나는 쪽에 전용 모듈이 없다.** 오픈소스 프로젝트가 라이선스 있는
상용 제품을 받아 시험하기 어려우니 자연스러운 결과다.

## 그런데 없어도 붙는다

에이전트에는 제품 이름이 아니라 **규격 버전**으로 나뉜 모듈이 따로 있다.

```
instrumentation/servlet/v2_2/    Servlet 2.2 ~ 2.5   javax, 비동기 없음
instrumentation/servlet/v3_0/    Servlet 3.0 ~ 4.0   javax, 비동기 있음
instrumentation/servlet/v5_0/    Servlet 5.0 이상    jakarta 로 패키지가 바뀜
```

WAS 가 어느 회사 것이든 Servlet 규격을 구현했다면 해당 규격 모듈이 붙는다.
JDBC 도 같은 구조다 — 드라이버별이 아니라 인터페이스 레벨에서 감싼다.

규격 네 세대를 대리 컨테이너로 실제로 확인해봤다. 에이전트 → 수집기 → 저장소 → 조회까지
전 구간을 탄 값이다.

| 컨테이너 | Servlet | JDK | 결과 |
|---|---|---|---|
| Tomcat 6 | 2.5 | 8 | 진입 스팬 잡힘 |
| Tomcat 7 | 3.0 | 8 | 잡힘 |
| Tomcat 9 | 4.0 | 8 | 잡힘 |
| Tomcat 10.1 | 6.0 (jakarta) | 17 | 잡힘 |

전부 `SpanKind = Server` 로 진입 스팬이 잡히고 `http.request.method` · `url.path` 가 채워졌다.

## 진짜 변수는 WAS 가 아니라 JDK 다

여기서 순서를 바꿔야 한다. 도입 검토할 때 "우리 WAS 를 지원합니까" 를 먼저 묻게 되는데,
**실제로 되고 안 되고를 가르는 것은 JDK 버전**이다.

에이전트 진입 클래스의 바이트코드 버전을 보면 나온다.

```
$ unzip -p opentelemetry-javaagent.jar \
    io/opentelemetry/javaagent/OpenTelemetryAgent.class | head -c 8 | od -An -tu1
  202 254 254 186   0   0   0  52
                                ^^ = Java 8
```

**최초 정식판(v1.0.0)부터 최신판까지 전부 52다.** 구버전을 찾아 내려가도 없다.
자바 6 은 50, 7 은 51 이고 JVM 은 자기보다 높은 번호를 **내용을 보지도 않고 거부한다.**
WAS 가 뜨기도 전에 끝난다.

그런데 상용 WAS 의 인증 JDK 가 생각보다 낮다. 제품 세대가 곧 JDK 세대라서,
오래된 WAS 가 도는 곳은 JDK 도 같이 오래됐을 가능성이 높다.

**같은 제품 같은 버전이라도 현장마다 JDK 가 다르다.** 그래서 제품 버전을 물어보는 것으로는
답이 안 나온다. 물어볼 것은 하나다.

```
$ $JAVA_HOME/bin/java -version
```

서버에 JDK 가 여러 개 깔린 경우가 흔하므로 **WAS 가 실제로 무엇으로 뜨는지**를 봐야 한다.

## JDK 가 낮으면

에이전트는 포기해야 하지만 관측 자체를 포기할 필요는 없다. 자바 버전과 무관한 경로가 있다.

**웹 서버 액세스 로그.** WAS 앞에 웹 서버를 두는 구성이 흔하고, 그 액세스 로그에는
요청마다 URL · 상태코드 · 처리 시간이 이미 찍히고 있다. 로그 수신기로 읽어 들이면
"어느 화면이 느린가" 는 답할 수 있다. 분산 추적은 아니지만 요청 단위 성능 데이터이고,
**코드를 한 줄도 만들지 않는다.**

**JMX.** 자바 5 부터 있는 기능이라 오래된 JDK 에서도 된다. 대상 JVM 안에 아무것도 넣지 않고
밖에서 포트로 접속해 힙 · GC · 스레드 · 커넥션 풀을 읽는다.

둘을 합치면 화면별 응답시간과 JVM 상태는 나온다. 빠지는 것은 한 요청이 서비스와 DB 를
거치는 내부 경로와 SQL 수행 시간이다.

## 정리

**"지원 목록에 없다" 가 "안 된다" 는 아니다.** 규격 기반으로 붙기 때문에 목록보다 넓게
커버된다. 전용 모듈이 없는 상용 WAS 도 Servlet 규격만 지키면 붙는다.

대신 물어볼 것의 순서를 바꾸는 편이 낫다.

```
1. JDK 가 몇인가            ← 되고 안 되고를 가른다
2. Servlet 규격이 몇인가    ← 어느 모듈이 붙는지
3. 전용 모듈이 있는가        ← 있으면 더 자세히 나온다
4. 한 대에 붙여본다          ← 마지막은 해봐야 안다
```

1 번이 답이 아니면 나머지를 물어볼 필요가 없고, 1 번이 답이면 나머지는 대체로 따라온다.
