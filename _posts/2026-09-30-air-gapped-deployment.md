국내 공공·의료·금융 현장에는 인터넷이 없는 구간이 흔하다. 서버실에 장비를 넣어도
바깥으로 나가는 길이 막혀 있다.

여기에 소프트웨어를 설치한다는 건 평소 습관을 하나씩 다 바꾸는 일이다.
`docker pull` 도 `apt install` 도 `pip install` 도 안 된다. 그런데 막상 해보면
이것들보다 **덜 예상했던 것**들이 더 자주 발목을 잡는다.

## 무엇이 막히나

명백한 것부터.

```
docker pull      레지스트리에 못 닿는다
apt / yum        저장소에 못 닿는다
pip / npm / go   패키지 저장소에 못 닿는다
```

여기까지는 누구나 예상한다. 문제는 그다음이다.

```
시각 동기        외부 NTP 서버에 못 닿는다
DNS              외부 이름 서버에 못 닿는다
인증서 검증      OCSP · CRL 조회가 막힌다
자동 업데이트    조용히 실패하며 로그만 쌓는다
```

**시각이 특히 고약하다.** NTP 가 안 되면 서버 시계가 조금씩 어긋나고, 어긋난 시계는
TLS 인증서 검증을 깨뜨린다. "어제는 됐는데 오늘 안 된다" 의 원인이 시계인 경우가
생각보다 많다. 그리고 관측 데이터는 **시각이 곧 데이터**라, 노드 간 시계가 어긋나면
트레이스의 앞뒤가 뒤집혀 보인다.

## 이미지를 나르는 법

컨테이너 이미지는 `docker save` 로 tar 로 뽑고 `docker load` 로 되살린다.

```
docker save -o images.tar image-a:tag image-b:tag ...
docker load -i images.tar
```

여기서 두 가지를 조심한다.

**아키텍처가 딸려간다.** 저장하는 시점의 아키텍처 하나만 들어간다. ARM 서버에 넣을
거면 ARM 장비에서 저장해야 한다. x86 노트북에서 만든 패키지는 열리지 않는다.

**크기가 커진다.** 관측 스택 한 벌이 압축해서 수 GB 다. 그런데 USB 를 FAT32 로
포맷하면 **파일 하나가 4 GB 를 못 넘는다.** 현장에서 받은 USB 가 FAT32 인 경우가
흔해서 이걸 전제로 나눠 담는 편이 안전하다.

```
split -b 3500m images.tar.gz part-
```

받는 쪽에서는 `cat part-* > 원본` 으로 합친다.

## 체크섬은 형식이 아니다

USB 로 수 GB 를 나르면 **실제로 깨진다.** 자주는 아니지만 겪으면 원인을 찾느라
반나절이 간다. 깨진 이미지는 `docker load` 단계에서 알 수 없는 오류로 나타나거나,
더 나쁘게는 로드는 되고 실행할 때 이상하게 동작한다.

```
sha256sum -c SHA256SUMS
```

이 한 줄을 절차에 넣어두면 그 반나절이 사라진다. 설치 스크립트가 자동으로 대조하게
만들어두는 편이 낫다 — 사람이 하는 검증은 바쁘면 건너뛴다.

## 패키지를 맥에서 만든다면

ARM 패키지를 Apple Silicon 맥북에서 만드는 경로를 쓰게 되는 경우가 있다.
그러면 **BSD 계열 명령어 차이**에 걸린다.

```
sha256sum       macOS 에 없다. shasum -a 256 을 쓴다
split -d        GNU 전용. BSD 는 숫자 접미사 옵션이 없다
```

`split -d` 는 `part-00`, `part-01` 처럼 숫자를 붙이고 BSD 는 `part-aa`, `part-ab` 처럼
알파벳을 붙인다. 합치는 쪽에서 `cat part-*` 로 glob 을 쓰면 **어느 쪽이든 정렬 순서가
유지되므로** 동작한다. 여기까지 생각해두면 제작 장비를 가리지 않는다.

## 이미지를 고를 때 라이선스를 본다

인터넷이 없으면 **레지스트리 인증이 필요한 이미지를 쓸 수 없다.** 현장에서 토큰을
갱신할 방법이 없기 때문이다. 그래서 구성 요소를 고를 때 기능만 보면 안 된다.

Kafka 를 예로 들면, 널리 쓰이던 Bitnami 이미지가 유료 전환됐고 Confluent 판은
Community License 제약이 있다. 오프라인 납품에는 **Apache 재단이 직접 내는
`apache/kafka` 가 적합**하다 — Apache 2.0 이고 인증 없이 받을 수 있다.

기능이 같아도 배포 조건이 다르면 오프라인에서는 다른 선택이 된다. 이건 도입 검토
단계에서 봐야지, 납품 전날 알면 늦다.

## 시각을 어떻게 맞추나

외부 NTP 를 못 쓰니 둘 중 하나다.

**현장에 NTP 서버가 있으면 그것을 쓴다.** 대개 있다. 반입 전에 주소를 받아둔다.

**없으면 하이퍼바이저 호스트를 시각 기준으로 삼는다.** 호스트에 `chrony` 를 세우고
VM 들이 거기를 보게 한다. 절대 시각은 틀릴 수 있지만 **노드 간 시각은 맞는다.**
관측 데이터에서는 이게 더 중요하다.

## DNS 를 안 쓰는 설계

이름 서버가 없으면 이름으로 서로를 못 찾는다. 그래서 처음부터 **IP 기반으로 설계**한다.

다만 IP 를 코드와 설정 곳곳에 박아두면 나중에 IP 가 바뀔 때 전부 뒤져야 한다.
컨테이너라면 `extra_hosts` 로 **이름 → IP 매핑을 한 곳에 모아두는 방법**이 있다.
서비스들은 계속 이름으로 서로를 부르고, 매핑만 고치면 된다.

인증서 SAN 도 이름으로 발급해두면 IP 가 바뀌어도 인증서를 다시 만들 필요가 없다.
IP 로 발급하면 IP 가 바뀔 때마다 재발급이다.

## 인증서 — 현장 IP 를 미리 모른다

내부 통신용 인증서는 우리가 직접 CA 를 세워 발급한다. 여기까진 어렵지 않은데
함정이 하나 있다.

**외부에서 접속하는 주소는 현장에 가야 정해진다.** 사무실에서 만든 인증서의 SAN 에는
사무실 IP 가 들어가 있고, 현장 IP 로 접속하면 인증서 이름이 안 맞아 경고가 뜬다.

그래서 반입 절차에 **인증서 재발급을 반드시 넣는다.** 그리고 재발급한 인증서를
**한 곳만이 아니라 관련된 모든 노드에 다시 배포해야 한다.** 웹 화면만 바꾸고 내부
통신용을 빼먹으면, 화면은 뜨는데 뒤에서 조용히 깨진다.

가능하면 반입 전에 고정 IP 를 미리 받아두고 인증서를 만들어 가는 편이 당일 작업을
크게 줄인다.

## 자동 업데이트를 끈다

`unattended-upgrades` 같은 자동 업데이트는 인터넷이 없으면 **실패하면서 로그만 쌓는다.**
당장 해롭지는 않지만 진짜 문제를 찾을 때 시야를 가린다. 반입 전에 끄는 편이 낫다.

같은 이유로 구독이 없는 상태의 기업용 저장소 설정도 정리한다. 실패한 갱신 시도가
매일 로그에 남는다.

## 설치 후 — 정말 인터넷을 안 쓰는지 확인하기

가장 확실한 검증은 **실제로 끊어보는 것**이다. 사무실에서 구축을 마친 뒤, 바깥으로
나가는 길을 막아놓고 전체를 재기동해본다.

이때 안 뜨는 것이 있으면 어딘가 인터넷에 의존하고 있다는 뜻이다. 기동 중에 무언가를
받아오거나, 외부 시각 서버를 기다리거나, 인증서 검증에서 외부 조회를 하고 있는 것이다.
**현장에서 발견하면 되돌릴 방법이 없다.** 사무실에서 미리 겪는 편이 훨씬 싸다.

## 정리

인터넷 없는 현장에 넣는 일은 기술적으로 어렵지는 않다. 다만 평소에 당연하게 쓰던
것들이 하나씩 빠지므로 **빠진 것을 미리 세어보는 절차**가 필요하다.

```
이미지     아키텍처 맞는 것으로, 인증 필요 없는 것으로, 체크섬 붙여서
시각       현장 NTP 또는 호스트 기준
이름       DNS 없이, 매핑은 한 곳에
인증서     현장 주소로 재발급, 전 노드에 배포
자동화     업데이트·구독 저장소 정리
검증       끊고 재기동해본다
```

마지막 줄이 나머지 전부를 대신한다. 끊어놓고 한 번 올려보면 빠진 것이 스스로 드러난다.
