ARM 서버가 국내에도 들어오기 시작했다. 코어당 전력이 낮고 코어 수가 많아서
동시성이 높은 워크로드에 유리하다는 이야기를 듣지만, 막상 올려보려면 다른 걱정이 앞선다.

**쓰던 게 그대로 돌아갈까.**

관측 스택 — ClickHouse, Kafka, OpenTelemetry Collector, PostgreSQL — 을 80 코어
ARM 서버에 통째로 올려보면서 확인한 것을 정리한다. 결론부터 말하면 대부분 된다.
다만 **"된다"를 미리 확인하는 절차**를 갖고 있지 않으면 현장에서 알게 된다.

## 첫 관문 — 컨테이너 이미지는 아키텍처에 묶인다

x86 에서 받은 이미지는 ARM 에서 안 돈다. 당연한 말 같지만 실무에서 이걸 놓치는
경로가 있다. **`docker pull` 은 알아서 맞는 걸 받아주기 때문**이다.

같은 태그가 여러 아키텍처의 이미지를 가리키는 구조(멀티 아키텍처 매니페스트)라,
평소에는 아키텍처를 의식할 일이 없다. 그런데 `docker save` 로 뽑아 옮기는 순간
**그때 받은 아키텍처 하나만** 딸려간다.

```
x86 노트북에서 docker save   →  amd64 이미지만 저장됨
ARM 서버에서 docker load     →  exec format error
```

그래서 ARM 서버에 올릴 이미지는 **ARM 장비에서 받아야 한다.** 손에 Apple Silicon
맥북이 있으면 그게 arm64 패키지 제작 장비가 된다.

## 무엇이 arm64 를 내놓는가

실제로 올려서 확인한 결과다. 컨테이너가 도는 상태에서 `docker image inspect` 로
아키텍처를 찍어보면 바로 나온다.

```
$ docker image inspect <이미지> --format '{{.Os}}/{{.Architecture}}{{if .Variant}}/{{.Variant}}{{end}}'
```

```
clickhouse/clickhouse-server:24.8-alpine        linux/arm64
apache/kafka:3.9.0                              linux/arm64
otel/opentelemetry-collector-contrib:0.120.0    linux/arm64
postgres:16-alpine                              linux/arm64/v8
eclipse-temurin:8-jre                           linux/arm64/v8
```

**주요 구성 요소는 전부 arm64 를 공식 배포한다.** 몇 년 전이었다면 직접 빌드해야
했을 것들인데 지금은 걱정할 필요가 없다.

`arm64` 와 `arm64/v8` 이 섞여 있는 게 눈에 띌 텐데, v8 은 ARMv8 아키텍처를 명시한
것이고 실질적으로 같은 것을 가리킨다. 둘을 구분해서 신경 쓸 일은 거의 없다.

## 자체 빌드 이미지는 직접 만들어야 한다

남이 만든 이미지는 해결됐고, 문제는 우리가 만드는 것이다. 애플리케이션 이미지는
당연히 아무도 arm64 판을 올려주지 않는다.

선택지는 둘이다.

**교차 빌드.** x86 장비에서 QEMU 에뮬레이션으로 arm64 이미지를 만든다. `buildx` 로
한 줄이면 되지만 **매우 느리다.** 명령어 하나하나를 소프트웨어로 번역하기 때문이다.
Go 컴파일처럼 CPU 를 많이 쓰는 단계가 있으면 체감이 크다. 한 번 해보고 포기했다.

**대상 장비에서 빌드.** ARM 서버 안에 빌드용 환경을 하나 두고 거기서 만든다.
네이티브라 빠르고, 만든 것이 실제로 도는 환경과 같다는 확신이 덤으로 온다.

우리는 후자를 택했다. 서버 안의 VM 하나에서 소스를 받아 빌드하고, 만든 이미지를
`docker save` 로 다른 VM 에 나른다. **호스트에는 Docker 를 설치하지 않는다** —
하이퍼바이저 호스트는 가볍게 두는 편이 낫다.

한 가지 덤이 있다. 빌드용 VM 을 두면 나중에 **현장에서 급히 고칠 일이 생겼을 때
그 자리에서 빌드할 수 있다.** 인터넷이 없는 현장이면 이 차이가 크다.

## 부팅이 다르다 — BIOS 가 없다

가상화까지 내려가면 x86 과 다른 점이 하나 나온다. **ARM 에는 레거시 BIOS 부팅이
없다.** UEFI 만 있다.

그래서 VM 을 만들 때 펌웨어를 UEFI(OVMF)로 잡아야 하고, 쓰는 OS 이미지도
**arm64 UEFI 부팅을 지원하는 것**이어야 한다. Ubuntu 의 arm64 클라우드 이미지는
문제없이 뜬다.

x86 습관대로 기본값으로 만들면 부팅이 안 되는데, 원인을 몰라 헤매기 쉬운 지점이다.

## 성능은 어땠나

80 코어 / 250 GB 구성에 관측 스택 전체를 5 개 VM 으로 나눠 올리고 부하를 넣었을 때,
**병목은 CPU 가 아니라 네트워크였다.** 초당 십수만 건을 받는 동안 서버는 여유가 있었고
1 GbE 회선이 먼저 찼다.

코어가 많다는 성질이 관측 워크로드와 잘 맞는다. 수집·적재·조회가 전부 병렬로 갈라지는
작업이라 코어 수가 그대로 처리량이 된다. 반대로 단일 스레드 성능이 중요한 작업이라면
다른 평가가 나올 것이다.

## 확인할 것 정리

ARM 서버 도입을 검토한다면 이 순서로 보면 대체로 답이 나온다.

**쓰려는 이미지가 arm64 를 내놓는가.** Docker Hub 의 태그 페이지에서 지원 아키텍처를
볼 수 있고, 이미 올려봤다면 `docker image inspect` 가 확실하다.

**자체 이미지를 어디서 빌드할 것인가.** 대상 장비에서 빌드할 수 있는 경로를 먼저
확보한다. 교차 빌드는 되긴 하지만 상시로 쓸 만하지 않다.

**네이티브 라이브러리를 쓰는 곳이 있는가.** JNI, CGO, 파이썬 C 확장처럼 컴파일된
바이너리를 품는 것들이 문제가 된다. 순수 자바나 순수 파이썬이면 아키텍처를 안 탄다.

**패키지를 어떤 장비에서 만들 것인가.** 오프라인 납품이면 여기가 실무상 가장 중요하다.
x86 노트북에서 만든 패키지는 ARM 서버에서 안 열린다.

## 남기고 싶은 것

몇 년 전에는 "ARM 에서 돌까" 가 진짜 질문이었다. 지금은 대부분의 인프라 소프트웨어가
arm64 를 공식 배포한다. 남은 진짜 문제는 **"우리 파이프라인이 아키텍처를 의식하고
있는가"** 다.

빌드가 어디서 도는지, 이미지를 어디서 받아 어디로 나르는지, 그 경로에 x86 장비가
끼어 있지는 않은지. 이걸 한 번 정리해두면 ARM 도입은 생각보다 싱겁게 끝난다.
정리하지 않으면 마지막 단계에서 `exec format error` 를 만난다.
