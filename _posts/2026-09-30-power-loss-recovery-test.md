데이터베이스 문서에는 "크래시 복구를 지원한다" 고 적혀 있다. 그런데 **실제로 전원을
끊어본 적이 있는가** 는 다른 질문이다.

무정전 전원 장치가 있어도 배터리가 다하면 같은 일이 벌어지고, 전원 계통 점검이나
차단기 사고는 UPS 뒤에서도 일어난다. 그래서 한 번은 해봐야 한다.

관측 스택(ClickHouse · Kafka · PostgreSQL)을 올린 서버의 전원을 강제로 끊고
무슨 일이 일어나는지 기록했다.

## 어떻게 재현하나

전원 케이블을 뽑는 게 가장 확실하지만 원격으로는 못 한다. 리눅스에는 **동기화 없이
즉시 리셋**하는 방법이 있다.

```
echo 1 > /proc/sys/kernel/sysrq
echo b > /proc/sysrq-trigger
```

파일시스템을 정리하지 않고 바로 리셋한다. 전원 차단과 같은 상태가 된다.
**돌아오는 명령이 없으므로 실행 전에 콘솔 접근 경로를 확보해둔다.**

가상화 환경이면 두 단계로 나눠 해보는 편이 낫다. 먼저 VM 만 강제 종료해보고
(하이퍼바이저가 프로세스를 죽이는 것), 그다음 호스트를 끊는다. 앞은 게스트
파일시스템만 더러워지고, 뒤는 **하이퍼바이저의 스토리지 계층까지** 더러워진다.

## 얼마나 걸렸나

```
전원 차단 → 호스트 부팅 완료      144 초
호스트 부팅 → VM 5 대 전부 기동    86 초
────────────────────────────────────
서비스 완전 복구                약 4 분 20 초
```

**사람 손은 필요 없었다.** 이게 가장 중요한 결과다. 복구에 수동 개입이 필요하면
새벽에 전화를 받게 된다.

## 살아남은 것

**LVM 씬 풀이 무사했다.** 씬 프로비저닝은 메타데이터가 깨지면 풀 전체를 못 여는
경우가 있어서 가장 걱정한 부분인데, 검사에서 정상이 나왔고 복구 도구를 쓸 필요가
없었다.

**ext4 저널이 자동으로 복구됐다.** VM 몇 대에서 저널 복구 메시지가 떴지만 전부
자동으로 끝났다. 수동 `fsck` 가 필요한 상태는 없었다.

**본체 데이터가 그대로였다.** 스팬 테이블과 요약 테이블의 행 수가 차단 전 기준선과
정확히 같았다.

## 흠집은 남았다

무사했다고만 쓰면 시험을 안 한 것과 같으므로, 남은 것을 적는다.

### 파트 17 개가 격리됐다

ClickHouse 가 기동하면서 쓰던 중이던 파트 17 개를 검증에 실패해 떼어냈다.
`detached` 디렉터리로 옮기고 서빙에서 제외하는 동작이다.

**이건 설계된 동작이다.** 손상 가능성이 있는 데이터를 조용히 섞어 내놓는 것보다
격리하는 편이 낫다. 실제로 떼어낸 것은 전부 0 MB 급의 자투리와 시스템 로그 테이블
이었고, 핵심 데이터 테이블에서는 하나도 나오지 않았다.

다만 **운영 관점에서 할 일이 하나 생긴다.**

```sql
SELECT table, count() FROM system.detached_parts GROUP BY table
```

격리된 파트는 디스크를 계속 차지한다. 자동으로 지워지지 않는다. 정전 후 점검
항목에 이걸 넣어두고, 내용을 확인한 뒤 정리해야 한다.

### 컨슈머 오프셋이 잘렸다

Kafka 쪽에서는 내부 토픽 하나가 손상돼 잘렸다.

```
CorruptRecordException: Found record size 0
Corruption found in segment ..., truncating to offset ...
```

어디까지 읽었는지 기록해두는 토픽이다. 이게 뒤로 잘리면 **이미 읽은 것을 다시 읽는다.**

여기서 방향을 짚어둘 필요가 있다. 이 사고는 **유실이 아니라 중복 쪽**이다.
실제로 확인해보니 중복이 나왔고, 비율은 전체의 0.00017 % 였다.

관측 데이터에서는 이 방향이 낫다. 없는 것보다 두 번 있는 편이 낫고, 중복은 조회
시점에 걷어낼 수 있다. 다만 **중복이 생길 수 있다는 것을 알고 설계해야** 한다 —
"정확히 한 번" 을 전제로 만든 집계가 있으면 그게 틀어진다.

## 시험에서 얻은 점검 목록

해보고 나서 평상시 설정에 반영한 것들이다.

**부팅이 멈출 조건을 없앤다.** `/etc/fstab` 에 적힌 디스크 중 하나라도 못 붙으면
부팅이 응급 모드로 떨어져 **콘솔에서 사람이 손대기 전까지 안 올라온다.** 원격
서버에서는 치명적이다. 필수가 아닌 마운트에는 `nofail` 을 붙이고 `pass` 를 0 으로
둔다. 이건 정전 시험을 하기 전에 먼저 확인해야 할 항목이다.

**자동 기동 순서를 정한다.** 데이터베이스가 뜨기 전에 애플리케이션이 붙으면
재시작 루프에 빠진다. 기동 지연을 주거나 의존 관계를 명시한다.

**정전 후 점검 항목을 문서로 만든다.** 격리된 파트 확인, 컨슈머 오프셋 확인,
행 수 대조. 새벽에 이걸 기억으로 하려고 하면 빠뜨린다.

## 무엇을 알게 되었나

가장 크게 남은 건 **"복구된다" 와 "사람 없이 복구된다" 는 다르다** 는 것이다.
문서에 적힌 크래시 복구는 대체로 작동한다. 문제는 그 과정에서 사람이 개입해야 하는
지점이 하나라도 있으면 새벽 4 시에 전화를 받는다는 것이다.

그래서 시험의 목표는 "데이터가 살아남는가" 가 아니라 **"아무도 안 깨우고 올라오는가"**
로 잡는 편이 낫다. 둘은 다른 질문이고, 뒤쪽이 운영에서 훨씬 중요하다.

그리고 한 번 해보면 점검 목록이 저절로 나온다. 위의 `nofail` 같은 것은 사고가
나기 전에는 아무도 생각하지 않는다.
