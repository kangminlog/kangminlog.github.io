스위치나 라우터를 감시 대상에 넣을 때 쓰는 것이 SNMP 다. 그런데 "SNMP 를 지원한다"
는 말은 생각보다 적은 것을 보장한다. **장비마다 내놓는 항목이 다르고, 같은 항목이
서로 다른 자리에 있기도 한다.**

연동하기 전에 무엇을 확인해야 하는지 정리한다.

## OID 라는 주소 체계

SNMP 의 모든 값에는 주소가 있다. 점으로 구분된 숫자다.

```
1.3.6.1.2.1.1.1.0     장비 설명 (sysDescr)
1.3.6.1.2.1.2.2.1.2   인터페이스 이름 (ifDescr)
```

길어 보이지만 앞부분은 고정된 나무 구조다. 실무에서 기억할 갈래는 둘이다.

```
1.3.6.1.2.1        표준 MIB     — 누가 만든 장비든 같은 자리
1.3.6.1.4.1        기업별 MIB   — 제조사마다 자기 구역
```

`1.3.6.1.4.1` 뒤에 붙는 번호는 IANA 가 제조사에 발급하는 고유 번호다. Cisco 는 9 번이다.
그래서 `1.3.6.1.4.1.9` 아래는 전부 Cisco 가 자기 마음대로 정한 값이다.

**표준 구역은 어느 장비든 같은 주소에 같은 뜻이고, 기업 구역은 제조사 문서를 봐야
안다.** 이 구분이 전부다.

## 표준 MIB 에서 얻을 수 있는 것

포트 상태와 트래픽은 IF-MIB 라는 표준에 있다. 대부분의 장비가 여기까지는 내놓는다.

```
1.3.6.1.2.1.2.2.1.2    ifDescr        이름
1.3.6.1.2.1.2.2.1.3    ifType         종류 (6=이더넷, 24=루프백, 131=터널)
1.3.6.1.2.1.2.2.1.7    ifAdminStatus  관리 상태 (1=사용, 2=사용안함)
1.3.6.1.2.1.2.2.1.8    ifOperStatus   실제 상태 (1=up, 2=down)
```

트래픽 카운터는 두 벌이 있다. **이게 실무에서 꼭 챙겨야 하는 부분이다.**

```
1.3.6.1.2.1.2.2.1.10      ifInOctets     32 비트
1.3.6.1.2.1.31.1.1.1.6    ifHCInOctets   64 비트
```

32 비트 카운터는 약 42.9 억 바이트에서 한 바퀴를 돈다. 1 Gbps 회선이 가득 차면
**34 초 만에** 넘어간다. 60 초 주기로 긁으면 그 사이에 한 바퀴를 돌아 계산이 틀어진다.
10 Gbps 면 3.4 초다.

64 비트 카운터는 같은 조건에서 수천 년이 걸린다. **기가비트 이상 회선이면 반드시
64 비트(`ifHC...`) 를 쓴다.** 장비가 64 비트를 안 내놓으면 폴링 주기를 크게 줄이거나
그 값을 신뢰하지 않아야 한다.

## 벤더 MIB 에만 있는 것

표준에 없는 것들이 있다.

```
온도 · 팬 상태 · 전원 이중화 · SFP 광 파워 · CPU · 메모리
```

CPU 와 메모리는 일부 장비가 HOST-RESOURCES-MIB(표준)로 내놓기도 하지만 일관되지 않다.
환경 센서는 사실상 전부 벤더 구역에 있다.

그래서 **"온도를 볼 수 있느냐" 는 장비를 봐야 답할 수 있는 질문**이다. 엔터프라이즈급
스위치는 대체로 나오고, 소형 스위치나 공유기는 센서 자체가 없는 경우가 많다.

없는 항목을 억지로 만들어내면 안 된다. 없으면 없다고 표시하는 게 맞다.

## 함정 하나 — 물리 포트가 표준에 없을 수 있다

이게 겪어보기 전엔 예상하기 어려운 부분이다.

소형 장비 중에는 **IF-MIB 에 물리 포트를 내놓지 않는 기종**이 있다. 리눅스 기반
장비에서 흔한데, IF-MIB 에는 운영체제가 보는 네트워크 인터페이스가 나온다.

```
lo      루프백
eth0    CPU 와 스위치칩 사이의 내부 연결
br0     LAN 포트 전체를 묶은 브리지
wg0     VPN 터널
```

24 포트짜리 장비인데 IF-MIB 에는 인터페이스가 대여섯 개만 보인다. **LAN 포트들이
스위치칩에서 이미 하나로 묶여 CPU 에 들어오기 때문**이다. 운영체제 입장에서는
브리지 하나일 뿐이다.

이런 장비의 물리 포트 정보는 벤더 구역에 따로 있다. 포트 수가 실물과 안 맞으면
거기를 뒤져야 한다.

## 연동 전 조사 순서

새 장비를 붙이기 전에 이 순서로 확인하면 대체로 파악된다.

**하나. 장비가 무엇인지 확인한다.**

```
snmpwalk -v2c -c <커뮤니티> -t 5 -r 2 <IP> 1.3.6.1.2.1.1
```

`sysDescr` 에 모델명과 펌웨어가 나온다. `sysObjectID` 는 `1.3.6.1.4.1.<제조사번호>...`
형태라 **여기서 제조사 번호를 알 수 있다.**

**둘. 인터페이스 목록을 본다.**

```
snmpwalk -v2c -c <커뮤니티> -t 5 -r 2 <IP> 1.3.6.1.2.1.2.2.1.2
```

여기 나오는 개수가 실물 포트 수와 맞는지 확인한다. 안 맞으면 위의 함정이다.

**셋. 64 비트 카운터가 있는지 본다.**

```
snmpwalk -v2c -c <커뮤니티> -t 5 -r 2 <IP> 1.3.6.1.2.1.31.1.1.1.6
```

비어 있으면 32 비트만 있는 장비다.

**넷. 벤더 구역을 통째로 훑는다.**

```
snmpwalk -v2c -c <커뮤니티> -t 10 -r 2 <IP> 1.3.6.1.4.1.<제조사번호> > vendor.txt
```

무슨 항목이 있는지 눈으로 본다. 자료형만 세어봐도 감이 온다.

```
grep -cE 'Counter32|Counter64|Gauge32' vendor.txt
```

**카운터 자료형이 하나도 없으면 그 구역에는 트래픽 통계가 없다는 뜻이다.**
문자열과 정수만 있으면 이름·상태·설정값뿐이다. 이걸 먼저 보면 헛수고를 줄인다.

## GETNEXT 와 GETBULK

`snmpwalk` 는 값을 하나씩 물어보는 GETNEXT 를 쓰고, `snmpbulkwalk` 는 여러 개를 한 번에
받는 GETBULK 를 쓴다. 수집 도구는 대부분 GETBULK 를 쓴다. 빠르기 때문이다.

그런데 **소형 장비 중에는 GETBULK 응답이 불안정한 기종이 있다.** `snmpwalk` 로는 잘
나오는데 수집기에서는 간헐적으로 timeout 이 뜬다면 이걸 의심해볼 만하다.

확인은 간단하다.

```
snmpwalk     -v2c -c <커뮤니티> -t 10 -r 1 <IP> <OID>   # GETNEXT
snmpbulkwalk -v2c -c <커뮤니티> -t 10 -r 1 <IP> <OID>   # GETBULK
```

한쪽만 성공하면 원인이 좁혀진다. 폴링 주기를 늘리거나 한 번에 긁는 OID 수를 줄이면
완화되는 경우가 있다.

## 정리

```
표준 MIB   포트 이름·상태·트래픽   →  대부분의 장비에서 나온다
           64 비트 카운터           →  있는지 확인할 것. 1G 이상이면 필수
벤더 MIB   온도·팬·전원·광파워      →  장비마다 다르다. 없을 수도 있다
           물리 포트                →  소형 장비는 여기 있을 수 있다
```

SNMP 연동에서 시간을 가장 많이 잡아먹는 건 설정이 아니라 **이 장비가 무엇을 내놓는지
모르는 상태로 시작하는 것**이다. 15 분쯤 들여 `snmpwalk` 를 돌려보고 시작하면
대부분 피할 수 있다.
