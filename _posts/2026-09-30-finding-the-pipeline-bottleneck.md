부하를 올리다 보면 어느 지점부터 처리량이 안 늘어난다. 이때 반사적으로 데이터베이스나
수집기를 의심하게 되는데, **재보면 엉뚱한 데가 천장인 경우가 많다.**

한 번은 초당 처리량이 특정 값에서 딱 멈췄다. 서버는 CPU 도 메모리도 여유가 있었고
디스크도 한가했다. 찾아보니 **네트워크 중간에 100 Mbps 구간이 하나 끼어 있었다.**

어떻게 찾았는지, 그리고 그 전에 무엇부터 봐야 하는지 정리한다.

## 먼저 환산부터 해본다

병목을 찾기 전에 **각 구간이 이론적으로 얼마까지 감당하는지**를 숫자로 적어두면
어디가 의심스러운지 바로 보인다.

관측 데이터는 건수로 말하고 네트워크는 비트로 말하니 환산이 필요하다.

```
1 GbE = 125 MB/s
스팬 1건이 선 위에서 약 650 B 라면
  125,000,000 ÷ 650 ≈ 초당 19 만 건
```

여기서 두 가지가 보인다. 첫째, **1 GbE 는 생각보다 많이 감당한다.** 초당 수만 건
수준이면 회선은 문제가 아니다. 둘째, 그럼에도 **초당 십수만 건을 넘기면 1 GbE 가
먼저 찬다.** 대규모 환경에서 10 GbE 를 쓰는 이유가 여기 있다.

그리고 100 Mbps 구간이 끼면 이 값이 10 분의 1 이 된다.

```
100 Mbps = 12.5 MB/s  →  초당 1.9 만 건
```

## 구간을 끊어서 잰다

네트워크가 의심되면 `iperf3` 로 구간별로 재는 게 가장 빠르다. 중요한 건
**물리 랜선을 타는 구간과 안 타는 구간을 구분해서 재는 것**이다.

```
# 받는 쪽
iperf3 -s

# 보내는 쪽
iperf3 -c <상대IP> -t 20
```

가상화 환경이면 이렇게 나뉜다.

```
같은 호스트 안의 VM ↔ VM     물리 랜선을 안 탄다
호스트 ↔ 다른 호스트          탄다
```

앞쪽이 수십 Gbit/s 인데 뒤쪽이 낮으면 **물리 경로에 문제가 있다**는 뜻이다.
실제로 재보니 이런 모양이었다.

```
호스트 내부 VM ↔ VM          51.0 Gbit/s     랜선 안 탐
다른 호스트 내부 VM ↔ VM     51.6 Gbit/s     랜선 안 탐
호스트 A → 호스트 B          91   Mbit/s     랜선 탐   ← 여기
호스트 A → 호스트 C        9,070   Mbit/s     랜선 탐
```

네 번째 줄이 결정적이다. **같은 출발지에서 다른 목적지로는 9 Gbit/s 가 나온다.**
즉 보내는 쪽도, 백본도 정상이다. 특정 목적지로 가는 경로에만 문제가 있다.

## NIC 협상 속도를 같이 본다

케이블이나 포트가 저속으로 협상된 경우가 흔하다. 양쪽에서 확인한다.

```
ethtool <인터페이스> | grep -E "Speed|Duplex|Auto-negotiation"
```

```
Speed: 1000Mb/s
Duplex: Full
```

여기가 `100Mb/s` 로 나오면 그 장비가 범인이다. 그런데 **양쪽 다 1000Mb/s 인데 실측이
91 Mbit/s** 라면 얘기가 다르다. 끝점은 멀쩡하고 **중간 장비가 100M** 라는 뜻이다.

오래된 스위치, 잘못 꽂힌 포트, 규격 미달 케이블이 흔한 원인이다. 사무실 배선은
몇 년에 걸쳐 조금씩 바뀌기 때문에 이런 구간이 남아 있는 경우가 생각보다 많다.

## 오류·드롭 카운터를 확인한다

속도가 맞는데도 느리면 오류를 본다.

```
ip -s link show <인터페이스>
```

`errors` 와 `dropped` 가 늘고 있으면 케이블·포트 문제이거나 버퍼가 넘치는 것이다.
둘 다 0 이면 네트워크 계층은 깨끗하다는 뜻이고, 그러면 위쪽을 봐야 한다.

## 병목이 망인지 확인하는 가장 쉬운 방법

부하를 거는 동안 **인터페이스 사용량이 이론 최대치에 붙어 있는지** 보면 된다.

```
sar -n DEV 1
```

앞의 실측에서 20 분 평균이 11.32 MB/s 였는데, 이건 91 Mbit/s 로 `iperf3` 실측
천장과 정확히 같은 값이다. **회선을 100 % 채우고 있었다.** 이러면 다른 곳을 아무리
튜닝해도 처리량이 안 늘어난다.

반대로 회선 사용량이 천장의 절반도 안 되는데 처리량이 안 늘면, 병목은 다른 데 있다.

## 그다음에 볼 곳

망이 깨끗하다면 이 순서로 내려간다.

**수집기가 거절하고 있는가.** OpenTelemetry Collector 는 자기 상태를 메트릭으로
내놓는다. 받은 수와 거절한 수를 대조하면 바로 보인다. 거절이 있으면 대기열이
차 있다는 뜻이고, 그건 더 아래가 못 받아준다는 뜻이다.

**중간 버퍼가 밀리고 있는가.** Kafka 를 끼웠다면 컨슈머 랙을 본다. 랙이 계속
늘면 넣는 쪽이 빼는 쪽보다 빠른 것이다. 랙이 0 근처면 이 계층은 여유가 있다.

**데이터베이스가 못 받는가.** 여기까지 와서야 데이터베이스를 의심한다. 적재 오류,
메모리 한도 초과, 디스크 대기 시간을 본다.

**보내는 쪽이 못 만들고 있는가.** 의외로 흔하다. 부하 생성기 자신이 천장인 경우다.
생성기를 늘렸을 때 처리량이 따라 늘면 범인은 생성기였다.

## 가장 중요한 습관

**보낸 건수와 적재된 건수를 항상 대조한다.**

```
발생기가 성공 응답을 받은 수  :  10,000,000
데이터베이스에 적재된 수      :   9,600,000
                                ───────────
                                  4 % 어딘가에서 사라짐
```

이 대조가 없으면 "느리다" 와 "잃고 있다" 를 구분하지 못한다. 그리고 이 둘은
완전히 다른 문제다. 느린 건 기다리면 따라오지만, 잃은 건 안 돌아온다.

숫자가 안 맞으면 계층마다 내려가면서 어디서 줄어드는지 본다. 보낸 수 → 수집기가
받은 수 → 버퍼에 들어간 수 → 적재된 수. 줄어드는 지점이 범인이다.

## 남기고 싶은 것

성능 문제를 만나면 대체로 **가장 복잡한 구성 요소를 먼저 의심한다.** 데이터베이스나
수집기 설정을 만지기 시작한다.

그런데 실제로는 **가장 단순하고 오래된 것**이 범인인 경우가 많다. 케이블, 스위치 포트,
협상 속도 같은 것들이다. 이런 건 튜닝으로 못 고치고, 재보기 전에는 안 보인다.

그래서 순서를 뒤집는 편이 낫다. **먼저 환산해서 이론값을 적고, 구간을 끊어 재고,
그다음에 위쪽을 의심한다.** 30 분이면 끝나는 절차이고, 며칠씩 엉뚱한 곳을 튜닝하는
것보다 훨씬 싸다.
